# Database Migration Plan

> Source: Ch. 23 §23.6, Ch. 9.
> **There is no database.** There is, however, a real migration problem, and it is easy to
> miss because it does not look like one.

---

## The actual migration problem

**The blueprint library is the one part of this product with copies living in other people's
repositories.**

Every generated file ends with a relative back-link to the blueprint it came from
(REQ-F-016). Those links are written once and never updated. So:

```
v1.0  ships blueprints/01-docs/04-technical-spec/technical-spec.md
      a developer generates a workspace; ~90 files now contain back-links to that path

v2.0  renames or moves that blueprint

      -> every back-link in every workspace ever generated now points at nothing
      -> and a broken back-link is INDISTINGUISHABLE from a generation bug
```

That is a schema migration in every way that matters: a structural change on our side,
breaking data that already exists on someone else's.

---

## Migration questions

| Question | Answer |
|---|---|
| Is the migration reversible? | For the **kit**: yes — publish the old path back. For a **workspace already generated**: the developer's version control is the only undo; the kit provides none. |
| Will existing data break? | An older workspace stays valid and readable — it is Markdown. What breaks is the **back-link**. |
| Can code and data deploy safely? | A developer's workspace and their installed plugin version can differ, permanently. **This is expected, not an error.** |
| Is downtime required? | No. Nothing runs. |
| **What must a version bump do?** | **Any release that renames, moves, or removes a blueprint is a MAJOR version and must ship a migration note naming old and new paths.** ADR-005's version stamp is what makes such a note actionable. |

---

## Migration types

| Change | Breaking? | Required action |
|---|---|---|
| Add a blueprint | No | Note it in the release |
| Edit a blueprint's **content** | No | Existing workspaces are unaffected — they hold copies, not references to content |
| Change a blueprint's **internal section structure** | No for existing workspaces; **yes** for regeneration consistency | Note it. Newly generated files will differ in shape from older ones |
| **Rename a blueprint file** | **YES** | Major version + migration note |
| **Move a blueprint to a different folder** | **YES** | Major version + migration note. Also changes back-link *depth* — the `../` arithmetic |
| **Remove a blueprint** | **YES** | Major version + migration note. Resume also cannot complete a stage that expects it |

## Migration note format

Shipped in the release notes. It is the whole mechanism, so it has to be mechanical:

```
### Migration — v1.x -> v2.0

Blueprints moved. Workspaces generated by v1.x carry back-links to the OLD paths.
Those links will not resolve against a v2.0 installation.

| Old path                                   | New path                              |
|--------------------------------------------|---------------------------------------|
| 01-docs/04-technical-spec/technical-spec.md | 01-docs/04-technical/technical-spec.md|

Your generated workspace is UNAFFECTED in content. Only the trailing "Blueprint:" line
of each file points at a path that has moved.

To check which version produced your workspace, see the version line in your spec/
entry-point file (ADR-005).

To fix: nothing is required. If you want the links to resolve, search-and-replace the
old prefix with the new one across spec/.
```

> **"Nothing is required" is the important sentence.** A broken back-link is a navigation
> inconvenience, not corruption. Saying so stops a developer from assuming their specs are
> damaged and regenerating a workspace they had hand-edited.

## What this project does **not** need

| Usual concern | Why absent |
|---|---|
| Up/down migration scripts | No schema. ADR-002 forbids scripts anyway. |
| Backfills before making a field required | No fields. |
| Deploy schema before dependent code | Nothing is deployed. |
| Staged migration for large tables | No tables. |
| Zero-downtime strategy | Nothing runs. |
| Data-loss risk from a careless change | **The nearest equivalent is real**: a rename with no migration note silently degrades every workspace ever generated. It costs no data, but it costs trust. |

> **Deployment caution (Ch. 23):** never treat database changes as ordinary code changes. A
> broken file can be redeployed; a careless database change can damage production data.
>
> **Translated:** never treat a blueprint **path** change as an ordinary content change. The
> content is yours; the path is a contract with every workspace you have ever produced.
