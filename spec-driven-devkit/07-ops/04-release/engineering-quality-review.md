## The questions specific to this project

Beyond the standard dimensions, four questions this product has to ask itself:

### 1. Did the specification survive contact with building?

> Success measure SM-4: *the change log and spec-change log have entries dated after coding
> began — i.e. the specs were updated rather than abandoned.*

If the last spec change predates the first code change, the workspace became documentation
during the build. **That is the failure this whole method exists to prevent, and this product
is the one place where it would be most embarrassing.**

### 2. Is the kit its own first user? (Q-006)

The kit generates spec workspaces. This workspace was generated by the method the kit
implements. Whether the kit — once built — is used to regenerate or maintain its own specs is
still open. **Whichever way it goes, it should be a decision.** A tool whose author will not
use it on itself is worth noticing.

### 3. Did the eval set grow from real intakes?

`ai-evals.md` says every real intake should contribute its answer script back. Invented cases
cover what we thought of; real ones cover what we did not. **If the golden set is still 36
invented cases at v1.0, the harness is measuring our imagination.**

### 4. What do the checks **not** cover?

Ask it directly, every time. It is the question that found the blueprint-coverage gap
(SC-010): fifteen validation checks and eighteen fitness functions all verified that what was
produced was correct, and **none verified that everything that should have been produced was**.

A workspace can be internally consistent, pass every check, and be missing an entire document.
No other item on this review would have found that — each one asks whether a rule holds, not
whether the set of rules is complete.

### 5. Are the `[TODO]`s shrinking or accumulating?

The workspace shipped with a known set of open items. Some are legitimately long-lived
(Q-003, Q-006). Others are release blockers (**Q-007**). A count that has not moved between
releases means the open-questions file has become a graveyard rather than a queue.

## The honest limit of this review

**One person reviews their own engineering** (CON-008). Every verdict above is
self-assessment, and self-assessment is systematically kind about the decisions it made.

The two cheapest counters, neither in place:

- **One hour of a second person's time**, cold, on the risk grid and this review. It is the
  same gap `risk-storming.md` names — a solo assessment structurally cannot produce a
  single-observer finding.
- **Evidence over judgement wherever possible.** Every metric above is a count from a file or
  a CI run, precisely because "does this feel healthy?" is the question a solo reviewer is
  worst at answering.
