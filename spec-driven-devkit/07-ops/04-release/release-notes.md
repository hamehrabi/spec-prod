## The migration note — why it is mandatory

**The blueprint library is the one part of this product with copies living in other people's
repositories.** Every generated file ends with a relative back-link to the blueprint it came
from. Rename that blueprint and every one of those links, in every workspace ever generated,
points at nothing — and a broken back-link is indistinguishable from a generation bug.

The version stamp (ADR-005) makes the mismatch **diagnosable**, but only against a note that
says what moved.

### Template

```
### ⚠ Migration — v1.x → v2.0

Blueprints moved. Workspaces generated by v1.x carry back-links to the OLD paths.
Those links will not resolve against a v2.0 installation.

| Old path | New path |
|---|---|
|          |          |

**Your generated workspace is unaffected in content.** Only the trailing
"> Blueprint:" line of each file points at a path that has moved.

To check which version produced your workspace, see the version line in your
spec/ entry-point file.

To fix: nothing is required. If you want the links to resolve, search-and-replace
the old path prefix with the new one across spec/.
```

> **"Nothing is required" is the sentence that matters.** Without it a developer assumes
> their specs are damaged and regenerates a workspace they had hand-edited — losing real work
> to a cosmetic problem.

## Writing rules

| Rule | Why |
|---|---|
| Write for the **developer**, not the maintainer | They are choosing whether to upgrade |
| Say what changes **for them**, not what changed in the repo | "Round 4 asks about drivers more clearly" beats "refactored questions.md" |
| A behaviour change in the interview **is** a user-facing change | Even though no interface moved |
| Name the version a defect affected, not just the one that fixes it | People on older versions need to know if it is them |
| **Never announce a metric collected from users** | There are none, and there never will be (CON-007) |
