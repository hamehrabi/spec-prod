# Edge Cases and Failure Conditions

> Source: Ch. 17 §17.7, Ch. 4 §4.6 (`failure-tests.md`), Ch. 30 §30.2.
> An **edge case** is an unusual but possible situation. A **failure condition** is a
> situation where the system cannot complete the request safely. Both must be planned
> before implementation — they are easy for AI agents to miss.

**Method:** start with the normal case, then ask what could be *empty, too long,
duplicated, expired, unavailable, unauthorized, or invalid*.

---

## The seven questions, answered for the intake run

| Question to ask | The case here | Case type | Expected result | Test |
|---|---|---|---|---|
| **What if the value is empty?** | The developer's free-text problem statement is one word, or blank | Edge | **Accepted, not rejected.** It becomes an open question with a decision owner. The interview never loops on an answer it does not like | FTEST-013 |
| | A round produces zero files because every question was inferable | Edge | The round is skipped **with a stated inference** — not rendered as an empty or failed round | FTEST-014 |
| | Validation finds zero failures | Edge | **"All 12 checks ran; all 12 passed."** Never a silent success — the count of checks *run* is the assertion | FTEST-005 |
| **What if the value is too long?** | The developer pastes 5,000 words as their problem statement | Edge | Accepted and used. Summarised into the brief; the full text is not discarded silently | FTEST-015 |
| | A generated workspace grows past what a validation walk can cover comfortably | Edge | Still validated fully. **This is the reopening trigger for performance as a driver**, and it is recorded, not handled | — |
| **What if the value is duplicated?** | The developer runs intake twice on a complete workspace | Edge | **Idempotent.** Reports complete, changes nothing, does not re-ask | FTEST-016 |
| | Two files try to mint the same identifier | Failure | Rejected. Identifiers are unique and never reused, even after a deletion | FTEST-012 |
| **What if the value is expired?** | A workspace was generated by an older plugin version whose blueprints have moved | Failure | The **version stamp** makes it diagnosable: the mismatch is named, not silently rendered as a broken link | FTEST-017 |
| **What if the user is not allowed?** | A write is required outside `spec/` | Security | Stops and asks, naming the path — never the file's contents | FTEST-003, STEST-002 |
| | The kit is asked, mid-interview, to write "just a quick example implementation" | Security | Refused, one sentence, boundary named, interview continues | STEST-001 |
| **What if the dependency fails?** | A blueprint is missing from the installed plugin | Failure | Stop at that file. Name it. **Prior rounds survive.** Never improvise a structure | FTEST-004 |
| | The repository is not writable | Failure | Fail **before** question one, naming the path — not after eight rounds of answers | FTEST-008 |
| | The host declines to produce something | Failure | Surface the refusal **verbatim**. Never paraphrase into a generic error | FTEST-018 |
| **What if the action is repeated?** | An interrupted stage is redone on resume | Edge | **Whole-file writes make it idempotent by construction.** Replace, never append | FTEST-001 |
| | A file fails its structural check twice | Failure | `[TODO]` + `Q-###` + a report line. **No third attempt** | FTEST-006 |

## The one that was nearly missed

> **Two sessions, one repository.** The concurrency row was about to be ticked off as
> *n/a — single user* on the reasoning that runs through this whole workspace: one developer,
> one machine, one repository. That reasoning is wrong by one word. *One machine* does not
> mean *one session*. Nothing stops a developer opening two Claude Code windows on the same
> project and starting an intake in each — and both would write to the same `spec/`, with no
> lock, no detection, and no state file that could hold one (ADR-004 forbids it).
>
> The likely outcome is two half-written stages interleaved, which resume would then treat
> as one incomplete stage and redo — possibly correctly, possibly not. **Nobody has checked.**
> It is logged as a `[TODO]` above rather than assumed away, because it is exactly the shape
> of thing this worksheet exists to surface: a category dismissed on a reason that sounds
> right and is off by one word.
>
> **Closed by decision, not by measurement (SC-008, 2026-08-08).** Concurrency handling is
> rejected for v1 and *one session per repository at a time* is the documented non-goal.
> *Nobody has checked* is still true, and the decision records that the work is declined —
> never that the collision is safe. The near-miss above stands as written: the row earned its
> place in this worksheet by almost being dismissed, and the dismissal it finally got is a
> dated decision with an owner instead of a reason that sounded right.

## The seven questions applied to the *generated* workspace

The questions above interrogate the kit. The kit must also make its **output** survive them —
that is what the developer is actually buying. Recorded here so the obligation is not lost
between the two meanings of "the system" (see the glossary in `project-brief.md`):

| Question | What the generated workspace must do |
|---|---|
| Empty | Table rows requiring a decision are never blank — either specified, or *"not needed, because…"* with a revisit trigger |
| Too long | The entry-point file is capped at 100 lines, because it loads into every context window |
| Duplicated | Identifiers unique within the workspace; never reused |
| Expired | The plugin version stamp lets a stale workspace be diagnosed |
| Not allowed | Every permission rule carries a **deny** test |
| Dependency fails | Every failure state carries a recovery path and a user message |
| Repeated | Task files are safe to re-read; re-running a task is not destructive |
