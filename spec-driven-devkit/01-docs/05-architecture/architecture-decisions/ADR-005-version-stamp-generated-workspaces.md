# ADR-005: Generated workspaces record the plugin version that produced them

**ADR ID:** ADR-005
**Status:** Accepted
**Date:** 2026-08-03
**Decision owner:** Kit author
**Review date:** Before the first release that renames or moves a blueprint

---

## Context

The blueprint library is the one part of this product that has **copies living in other
people's repositories**. Every generated file ends with a relative link back to the blueprint
it came from (REQ-F-016), and those links are written once and never updated.

The consequence is a migration problem that does not look like one. If version 2 renames
`technical-spec.md` or moves it to a different folder, every workspace ever generated by
version 1 now has a back-link pointing at nothing — and a broken back-link is
indistinguishable from a generation bug. Nobody can tell whether the workspace was produced
incorrectly or produced correctly by an older library.

There is no database to migrate and no schema to version. The question is only whether a
workspace can say who made it.

## Options considered

1. **No stamp** — workspaces carry no version information.
   *Benefit:* nothing to write, nothing to keep accurate, nothing that churns in diffs.
   Perfectly adequate while exactly one version exists.
   *Cost:* the cost is entirely deferred onto whoever ships version two, and it lands as
   unexplainable support reports. A developer with a broken link has no way to know their
   workspace predates a rename, and neither does anyone helping them.

2. **Stamp the plugin version** — one line recording the version that produced the workspace.
   *Benefit:* a broken link becomes diagnosable in one step: compare the stamp to the
   installed version, and a mismatch explains it. Makes a migration note actionable — the
   note can say "workspaces stamped below 2.0.0 have back-links to the old paths".
   *Cost:* one more thing to keep correct, and it must be written by the same process that
   can get things wrong. A stamp that is absent or stale is worse than useless if anyone
   trusts it.

3. **Stamp version and generation timestamp.**
   *Benefit:* everything option 2 gives, plus the ability to spot a stale workspace and to
   correlate with support reports.
   *Cost:* the timestamp changes on every regeneration, so it churns in git diffs on files
   that are otherwise unchanged — noise in exactly the artifact that is supposed to make
   change reviewable. It also records when, which nobody asked for, to answer a question
   nobody has.

*Compared on:* what question the recorded fact actually answers · what it costs when it is
wrong · what it costs in review noise.

## Decision

**Stamp the plugin version. Not the timestamp.** The version that produced the workspace is
recorded once, in the workspace's entry-point file.

## Reason

Option 3's timestamp answers "when", and the problem is "which library". Version answers the
question exactly; the timestamp adds churn to every diff to answer something else. Option 1
is correct today and wrong on the day of the second release — and the second release is the
one that will rename something, because that is when the library's structure gets revised
against real use.

The deciding argument is that this stamp is what turns a **silent** failure into a **named**
one. Everything else in this workspace is built on making gaps visible rather than filling
them; a broken back-link with no explanation is exactly the kind of invisible gap the rest of
the method exists to prevent.

## Consequences

- **Positive:** A broken back-link is diagnosable rather than mysterious. Migration notes
  can name a version boundary. Support becomes a one-question conversation.
- **Trade-off or limitation:** The stamp is written by the same instruction-driven process
  that can misread an instruction (ADR-002), so it can be absent or wrong — and a *wrong*
  stamp is worse than none, because it will be trusted. It also means the entry-point file
  changes on every plugin release even when nothing else does.
- **Rule the AI assistant must follow during implementation:** Write the plugin version into
  the generated entry-point file. Do not write a generation timestamp. Do not invent a
  version — read it from the plugin manifest; if it cannot be read, write
  `[TODO: plugin version could not be determined]` rather than a guess.

| Enforced by | Where |
|---|---|

## Revisit when

- The blueprint library's paths stabilise permanently and no rename is ever expected again.
  The stamp then costs a line and buys nothing — though by that point removing it costs more
  than keeping it.
- A second thing needs versioning independently of the plugin — for example if the blueprint
  library were ever distributed separately. Then the stamp needs to name which of the two,
  and this ADR is superseded rather than amended.

## Impact

| Dimension | Impact |
|---|---|
| Security | None. |
| Reliability | Positive. Converts a silent, unattributable failure into a diagnosable one. |
| Performance | None. |
| Cost | One line per workspace, plus the discipline to ship migration notes on breaking releases. |
| Maintainability | Positive for support; slightly negative for diff noise on the entry-point file. |
